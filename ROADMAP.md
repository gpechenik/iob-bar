# iob-bar — Roadmap

This document captures planned future work and design decisions for iob-bar
and its potential companion apps.

## Status as of 2026-04-28

**iob-bar v1 is functionally complete and in daily use.** No further changes
are required to ship it as-is.

What works:

- Menubar item displays current IOB, recomputed every minute as time passes
- Click or `⌃⌥⌘I` opens a popover with the IOB number, all active doses, and
  per-dose contributions after pharmacokinetic decay
- Quick-add buttons `+0.5u` / `+1.0u` / `+1.5u` / `+2.0u` with keyboard
  shortcuts `1`–`4`
- Custom-amount + minutes-ago entry for back-dating
- Hover-X to remove a dose; IOB recalculates immediately
- AM/PM basal tracking with midnight rollover, also Once-per-day and Off modes
- JSON persistence to `~/Library/Application Support/iob-bar/`
- Global hotkey `⌃⌥⌘I` via the `KeyboardShortcuts` Swift package

## Deferred polish (small)

These would be nice but aren't blocking daily use.

### Settings UI

The `AppSettings` struct exists with everything in it (peak activity time,
action duration, basal mode, default dose amounts), and `SettingsStore`
persists it to JSON. There's no UI yet. To build:

- Open via `,` keyboard shortcut from the popover, or a gear icon
- Stepper for peak activity minutes (default 75)
- Stepper for action duration minutes (default 360)
- Picker for basal tracking mode (AM/PM, once-per-day, off)
- TextFields/Steppers for the four default-dose amounts
- `KeyboardShortcuts.Recorder("Toggle popover", name: .togglePopover)` for
  rebinding the global hotkey
- Reset-to-defaults button

This is the highest-value next addition — until it exists, changing any
setting requires editing source and rebuilding.

### Test target population

The Swift Testing target (`iob-barTests/`) was generated by Xcode but is
empty. Mirror LoopKit's `InsulinMathTests`:

- `model.fractionRemaining(at: 0)` ≈ 1.0
- `model.fractionRemaining(at: actionDuration)` ≈ 0.0
- `model.fractionRemaining(at: peakActivityTime)` ≈ 0.69 for Humalog adult
  (verify against LoopKit's reference output)
- `IOBCalculator.currentIOB` of an empty list = 0.0
- `IOBCalculator.currentIOB` of one dose at t=0 = the full dose amount
- Dose pruning: a dose older than `actionDuration` is dropped on `prune()`

### Menubar item width

We attempted to narrow the menubar item by switching from
`MenuBarExtra(_:content:)` to the `MenuBarExtra(content:label:)` form. If
this didn't visibly tighten the rendering, the only remaining lever is
dropping out of `MenuBarExtra` entirely and using `NSStatusItem` directly.
That's a real refactor (~50–150 lines, lose `MenuBarExtraAccess` benefits,
gain full layout control). Worth doing only if the halo bothers daily use.

### Launch at login

After copying `iob-bar.app` to `/Applications/`, auto-launch is currently a
manual step (System Settings → General → Login Items → +). A first-class
in-app toggle would use `SMAppService.mainApp.register()` (macOS 13+):

- Add a "Launch at login" toggle in the (planned) Settings UI
- Bind to `SMAppService.mainApp.status == .enabled`
- Toggle on: `try SMAppService.mainApp.register()`
- Toggle off: `try SMAppService.mainApp.unregister()`

~10–20 lines once the Settings UI exists.

### v1 binary size baseline

For regression watching: v1 Debug build is **2.3MB unzipped / 564KB zipped**.
Release would be smaller. If a future change significantly inflates this
(e.g. adding a heavy framework dependency), that's worth noticing — staying
small is part of the design philosophy, not just an accident.

### HealthKit on macOS

HealthKit availability for native macOS apps has expanded across recent
macOS versions but is still inconsistent. Research current state and consider
migrating dose persistence to HealthKit's `HKQuantityTypeIdentifierInsulinDelivery`.
Benefits:

- Free iCloud sync, including to a future iOS app
- Integration with the diabetes app ecosystem (Loop, AAPS readers, Tidepool)
- Survives device migrations via iCloud Health backup
- Notes can persist in `HKQuantitySample.metadata`

**Trigger**: until HealthKit is in place, cross-machine sync uses a manual
symlink from inside the App Sandbox container to a synced directory (iCloud
Drive, etc.); see the README. macOS sometimes recreates the symlink target
during system updates. When that becomes annoying enough to merit the
~hours of HealthKit integration work, do it then.

## iPhone port

When this happens:

1. **Apple Developer account** — required for App Store distribution and for
   running the app on a physical iPhone for more than 7 days at a time.
   $99/year via developer.apple.com.
2. **Bundle ID** — current is `graham.gg.iob-bar`. Same bundle ID for both
   Mac and iOS keeps HealthKit authorizations and the user identity unified;
   different IDs would be two separate "apps" from the OS's perspective.
3. **Architecture** — SwiftUI app + WidgetKit. iOS 17+ for interactive widgets.
4. **Storage** — HealthKit. Both Mac (when available) and iOS read/write
   `HKQuantityTypeIdentifierInsulinDelivery`. iCloud syncs automatically.
5. **Interactive widget** — the dream UX. Tap a widget to log +0.5u directly
   from the home screen using WidgetKit + App Intents. Requires iOS 17.
6. **Watch complication** — out of scope for v1, but a watchOS complication
   showing IOB on the watch face would be the platonic ideal of glanceability.

## Companion app: BG menubar (working name `bg-bar`)

A separate-but-sibling app that displays current Dexcom CGM blood glucose
in the menubar. Replaces tools like Luka Mini with a self-built minimal
viewer.

### Why a separate app, not an addition to iob-bar

- **Design philosophy stays intact**: iob-bar's purity ("one number, the
  active doses, that's it") is a design value, not an oversight. Adding
  BG would compound concerns.
- **Failure isolation**: Dexcom Share auth can break (token expiration,
  password change, network issues). Keeping it out of iob-bar means a
  Dexcom outage doesn't take down dose-logging.
- **Code surface**: BG adds network code, Keychain credential storage,
  refresh-token handling, error states for offline operation. iob-bar
  has zero network code today; this is worth preserving.
- **Menu real-estate**: two small menubar items eat slightly more space
  than one combined item, but the user has consistently expressed
  preference for surgical, single-purpose tools.

### Architecture

- macOS menubar app, same approach as iob-bar (SwiftUI `MenuBarExtra`)
- Optional iOS app + widget, mirroring the iob-bar iPhone port plan
- Stack: Swift + [`kylebshr/dexcom-swift`][dexcom-swift] (Swift port of
  pydexcom)
- Auth: Dexcom Share username + password, stored in macOS Keychain
  (never on disk). Region defaults to US (also OUS, JP available).
- Polling: every 5 minutes (Dexcom updates every ~5 min). Use
  `BGTaskScheduler` or a foreground `Timer`.
- CGM: Dexcom G7 (the user's hardware). dexcom-swift / pydexcom claim to
  support G4/G5/G6/G7 via Share; verify on first run.

### Display

- **Menubar**: just the BG number (e.g. `87`) plus a trend arrow
  (`→` flat, `↗` rising, `↘` falling, `↑` rapid rise, `↓` rapid fall).
- **Optional color tier**: low/normal/high. Conflicts somewhat with the
  user's "no colors" preference; resolve by making colors *opt-in* via
  setting, default off, with maybe an exception for genuinely urgent
  thresholds (sub-70, above-250) using SF Symbols' tinted variants.
- **Popover**: current BG, last-N readings as a sparkline (text-based
  or emoji bars — keep simple), refresh-now button, settings entry.

### Dexcom Share auth flow (per pydexcom)

The Dexcom Share service requires a Dexcom account with at least one
follower configured to enable sharing. The app uses *user* (or dependent's)
credentials, not the follower's. Three valid identifier forms accepted:

- Phone number (`+11234567890`)
- Email (`user@email.com`)
- Account ID (UUID, advanced)

### Show absolute time in dose rows

Each active-dose row currently shows only relative time (`1h00m ago`).
Adding the absolute clock time alongside (`1h00m ago · 9:45 PM`) would
save the user mental arithmetic — same affordance the custom-entry section
already provides via its "(= 9:45 PM)" hint.

**Wrinkle**: the popover is 280px wide and the row layout is tight. Naively
appending the absolute time will overflow. Resolve via either widening the
popover to ~320px, moving to a two-line row, showing absolute time only on
hover, or shrinking the contributing-amount text. Worth a small design pass
when implementing.

### Editable amount / minutes-ago fields in custom entry

The Stepper for "Minutes ago" is fine for small adjustments but tedious
for back-dating a couple of hours (24 clicks at the 5-minute step). Convert
each Stepper to a TextField+Stepper hybrid so users can type a value
directly. Same for the dose amount. ~3-character-wide fields would capture
up to 99.5u and 999 minutes, which is plenty.

### Optional toggle: hide basal section

Some users won't want the basal section in the popover even when basal
tracking is otherwise useful. Add a setting that hides the AM/PM (or daily)
basal section without losing the basal-tracking mode itself — distinct from
the existing `BasalTrackingMode.off` (which suppresses tracking entirely).

### Cross-machine sync (symlink today, HealthKit later)

The current sync story (manual symlink inside the App Sandbox container,
documented in the README) is a bridge, not a destination. macOS occasionally
recreates container subdirectories during system updates or when sandbox
grants change, clobbering the symlink. The natural prompt to upgrade to
HealthKit-backed storage is "symlink-recreation has become annoying enough
to merit the work." See the HealthKit on macOS section above.

### Bootstrap shortcut for next time

iob-bar was built scaffold-first: Swift sources in `Sources/`, then merged
into Xcode's auto-generated project via `mv` and `git mv`. It worked but
required a directory-rename dance to dodge Xcode's "folder must not exist"
wizard behavior, plus several rounds of "fix the first build" import
errors that wouldn't have surfaced if I'd been able to compile as I wrote.

For bg-bar (or any next Mac project), consider either:

- [**XcodeGen**](https://github.com/yonaskolb/XcodeGen) — describe the
  project structure in YAML, generate `.xcodeproj` on demand. Standard tool
  in larger iOS/Mac codebases; cuts the bootstrap to "create folder + write
  Package.yml + run xcodegen."
- **Have Claude write the `.pbxproj` directly** — it's editable text (Apple's
  legacy ASCII plist format) and Claude can produce one matching Xcode's
  auto-generated structure. Brittle but works for small projects.

Either avoids the manual merge step.

## Notes for next session

- Repo is public at https://github.com/gpechenik/iob-bar
- Bundle ID is `graham.gg.iob-bar` (already chosen). Keep it stable to
  avoid re-granting macOS permissions on each rebuild.
- The medical disclaimer in the README must remain on any distribution.
  Strengthen it further if pursuing any kind of broader release (App Store,
  Homebrew cask, etc.).
- All major design decisions to date are documented in commit messages and
  in this file, but the load-bearing ones to NOT relitigate without a strong
  reason are:
  - Exponential pharmacokinetic model (not Walsh, not linear)
  - JSON persistence (not Core Data, not SwiftData) — until HealthKit takes
    over
  - Sibling app for BG (not bloating iob-bar)
  - No graphs, no carb tracking, no BG correlation in iob-bar itself
  - Keep the popover's "active doses" list newest-at-bottom (chat-app
    convention; doses appear adjacent to the buttons that produced them)
